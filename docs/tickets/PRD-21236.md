## Requirement understanding

One line: Manage email security policies, review quarantine, and analyze threats via Mimecast.

The reporter wants an AI agent to be able to do three things against Mimecast (the MSP email
security gateway): manage email security policies, review quarantined (held) mail, and analyze
threats (TTP logs, remediation incidents, admin audit). The ticket is a one-line capability
request plus a reference link (`https://conduit.wyre.ai/plugins/mimecast`, an internal connector
catalog entry) — per `references/mcp-track.md` §2.1 this kind of link is reference material, not a
requirement in itself, and is not treated as evidence of what capabilities already exist.

JS-rendered SPA that a static fetch cannot read past its shell):

- Legacy action-style API (the same family every existing tool in this repo already calls,
  `POST https://api.services.mimecast.com/api/...` with a `{"data": [...]}` envelope):
  `/api/policy/blockedsenders/get-policy` and `/api/policy/antispoofing-bypass/get-policy`
  (confirmed via `integrations.mimecast.com/documentation/endpoint-reference/policies/...` and the
  Cortex XSOAR `mimecast-v2` integration's `mimecast-list-policies` / `mimecast-get-policy`
  commands, which map a `policyType` of `blockedsenders` / `antispoofing-bypass` /
  `address-alteration` to these per-type endpoints), each requiring the `Gateway | Policies | Read`
  permission on the API application's role.
- `POST /api/managedsender/permit-or-block-sender` — permits or blocks one external sender for one
  internal recipient mailbox (bypasses or rejects, respectively), requiring
  `Gateway | Managed Senders | Edit`. Confirmed via
  `developer.services.mimecast.com/docs/cloudgateway/1/routes/api/managedsender/permit-or-block-sender/post`
  and the mirrored `integrations.mimecast.com` reference page.
- A newer, separate REST-style family also exists
  (`GET https://api.services.mimecast.com/policy-management/cloud-gateway/v1/...`, e.g.
  `anti-spoofing/policies`, `blocked-senders/policies`, `greylisting/policies`,
  `delivery-route/policies`) but it is a plain-GET, no-envelope shape that
  `src/mimecast_mcp/api_client.py` does not support today — see "Option analysis" below for why
  this design does not use it.

## Product design

### Goals / Non-goals

**Goals**

- Give the agent visibility into the Mimecast email-security policies that govern how mail is
  filtered, so "manage ... policies" has something to read.
- Give the agent the one Mimecast operation that most directly matches a day-to-day "manage
  policy" action an MSP operator takes after reviewing quarantine: permit or block a specific
  sender for a specific mailbox.
- Keep the blast radius of any new write tool at or below the one write tool this server already
  ships (`mimecast_release_message`): single-item, explicit `confirm: true` required, never
  retried blindly.

**Non-goals (this ticket)**

- Creating, editing or deleting account-wide policies (anti-spoofing, blocked-senders, etc.). These
  change mail flow for every mailbox on the account; see Open Question OQ2.
- The `address-alteration` policy type. Its endpoint was not independently confirmed from a
  quotable source during this design; see Open Question OQ1.
- Anything already covered ("review quarantine", "analyze threats") — no changes needed there.

### Acceptance criteria AC1..ACn

- **AC1** — Given valid Mimecast credentials whose role has `Gateway | Policies | Read`, When the
  agent calls `mimecast_list_policies` with `type` = `blockedsenders` or `antispoofing-bypass`,
  Then the tool returns the policies of that type as a JSON list with `count`, `has_more` and
  `next_page_token`.
- **AC2** — Given a policy `id` returned by AC1, When the agent calls `mimecast_get_policy(type,
  id)`, Then it returns that single policy's fields; Given an `id` Mimecast does not recognize,
  Then it returns a `not_found` error envelope (not an exception, not an empty 200).
- **AC3** — Given a sender address and a recipient mailbox address, When the agent calls
  `mimecast_manage_sender(action, sender, to)` **without** `confirm: true`, Then nothing is sent to
  Mimecast and the tool returns `{"done": false, ...}` describing the pending action, exactly like
  `mimecast_release_message` behaves today.
- **AC4** — Given the same call repeated **with** `confirm: true` after the user approved it, Then
  the tool calls Mimecast's permit-or-block-sender operation and returns `{"done": true, ...}` on
  success, or the standard structured error envelope (not a raw exception) if Mimecast rejects it
  (e.g. missing `Gateway | Managed Senders | Edit`).
- **AC5** — Given credentials with insufficient permission for any of the three new tools, Then the
  error envelope's `code` is `unauthorized` — the same generic mapping every existing tool already
  gets from `classify_status`, with no special-casing needed.

### Open questions

- **OQ1** (not blocking) — `address-alteration` is a valid Mimecast `policyType` (per the XSOAR
  reference), but unlike `blockedsenders` and `antispoofing-bypass`, its exact endpoint path was
  not independently confirmed from a quotable source while writing this design (the only mention
  found was in the context of an unrelated "Address Alteration Set" folder reference on a
  different endpoint). **Decision**: V1 ships `blockedsenders` and `antispoofing-bypass` only.
  Add `address-alteration` as a follow-up once its endpoint is confirmed against the live
  OpenAPI spec or a sandbox account — do not guess the path.
- **OQ2** (not blocking) — "Manage ... policies" could be read as full CRUD on account-wide
  policies. Creating or editing an anti-spoofing or blocked-sender policy changes mail filtering
  for the whole account and is a materially larger blast radius than anything this server does
  today (one bad policy can hold or reject legitimate mail org-wide). **Decision**: V1 scopes
  "manage" to (a) read visibility into existing policies, and (b) the lowest-blast-radius write
  Mimecast exposes for this purpose — permit/block **one sender for one mailbox** — gated by
  `confirm: true` exactly like `mimecast_release_message`. This is consistent with the other two
  verbs in the same ticket sentence ("review", "analyze") also being read/inspect-oriented. If the
  requester actually needs account-wide policy CRUD, that is a materially different, higher-review
  follow-up ticket, not an assumption to bake in here.
- **OQ3** (not blocking) — The exact JSON field names `get-policy` returns for each type beyond
  what public sources confirm (e.g. for anti-spoofing: `id`, `description`, `option`, `fromPart`,
  `fromDateTime`/`toDateTime`, `fromEternal`/`toEternal`, `override`, `bidirectional`) should be
  verified against the live OpenAPI spec or a sandbox account during implementation. Not blocking:
  the tool is a thin pass-through (same pattern as every existing list/get tool in this repo,
  several of which carry the same "not checked against a live account" caveat in today's
  `README.md` Delivery notes).

## Tech design

### Conclusion

Add one new module, `src/mimecast_mcp/tools/policies.py`, exposing three tools
(`mimecast_list_policies`, `mimecast_get_policy`, `mimecast_manage_sender`) built entirely on the
existing `api_client` / `run_tool` / `listing` infrastructure. No change to `api_client.py`: the
three new operations use the exact same `POST /api/...` + `{"data": [...]}` transport every
existing tool already uses. Wire the module into `navigation.py` (new `"policies"` domain) and
`server.py` (registration + `INSTRUCTIONS`), extend the test contracts
(`tests/test_tools.py`, `tests/contract_types.json`) and `tests/test_api_client.py`, and document
the new tools in `README.md` and `pyproject.toml`.

### Option analysis

**Option A — chosen.** Implement the three tools against the legacy action-style endpoints
(`/api/policy/{type}/get-policy`, `/api/managedsender/permit-or-block-sender`), reusing
`MimecastClient.call` unchanged. This is the same endpoint family and request shape every one of
the 11 existing tools already uses successfully in production.

**Option B — rejected.** Use the newer REST-style `policy-management/cloud-gateway/v1/...` `GET`
endpoints found during research. Rejected because: (1) they are plain `GET` calls with no
`{"data": [...]}` envelope and no pagination-meta shape confirmed to match `MimecastClient.call`'s
assumptions — adopting them means extending `api_client.py` itself against an API shape this
design could not fully verify (the developer portal is a client-rendered SPA that a static fetch
cannot read past its shell); (2) the confirmed action-style endpoints already satisfy AC1-AC4 with
zero client-layer risk. Revisit if a future ticket specifically needs a field that only exists on
the v1 policy-management resources.

**Option C — rejected.** Implement full create/update/delete for account-wide policies now.
Rejected per OQ2 — out of proportion to what the ticket asks for, and a materially different risk
tier with no human available this round to confirm the risk appetite.

### Data & API contract

```
mimecast_list_policies(type: "blockedsenders" | "antispoofing-bypass",
                        page_size?: int, page_token?: str) -> str (JSON)
  -> {"policies": [...], "count": int, "has_more": bool, "next_page_token": str | null}
  Calls: POST /api/policy/{type}/get-policy  body {"data": [{}]}
  Permission: Gateway | Policies | Read
```

```
mimecast_get_policy(type: "blockedsenders" | "antispoofing-bypass", id: str) -> str (JSON)
  -> {<policy fields, pass-through>}                      on success
  -> {"error": {"code": "not_found", "message": ..., "retryable": false}}   when id is unknown
  Calls: POST /api/policy/{type}/get-policy  body {"data": [{"id": id}]}
  Permission: Gateway | Policies | Read
```

```
mimecast_manage_sender(action: "permit" | "block", sender: str, to: str,
                        confirm?: bool) -> str (JSON)
  without confirm: true  -> {"done": false, "action": "...", "message": "..."}  (no network call)
  with confirm: true     -> {"done": true, "id": ..., "sender": ..., "to": ..., "type": "Permit"|"Block"}
                         -> structured error envelope if Mimecast rejects it
  Calls: POST /api/managedsender/permit-or-block-sender
         body {"data": [{"action": action, "sender": sender, "to": to}]}, read=False
  Permission: Gateway | Managed Senders | Edit
```

No database, no migration — this server is stateless (credentials arrive per request, nothing is
persisted). Purely additive: no existing tool's request or response shape changes, so there is
nothing to version or deprecate.

### Key flow / sequence

1. Agent calls `mimecast_list_policies(type="blockedsenders")` → sees existing policies and their
   `id`s.
2. Agent calls `mimecast_get_policy(type="blockedsenders", id=...)` for detail on one policy, if
   needed.
3. Agent reviews quarantine (`mimecast_list_held_messages`, already shipped) and threat data
   (already shipped), decides a sender should be permitted or blocked going forward, and describes
   the action to the user.
4. Agent calls `mimecast_manage_sender(action, sender, to)` without `confirm` → gets back the
   pending-approval message → relays it to the user.
5. User approves → agent calls `mimecast_manage_sender(action, sender, to, confirm=true)` → the
   sender is permitted or blocked for that mailbox.

### Non-functional

- **Multi-tenant / credential isolation**: unchanged — every tool still reads credentials from the
  per-request `GatewayCredentialsMiddleware` context var (`server.py:83-124`); nothing is ever
  stored at module level. This is enforced generically, not per-tool, so the existing
  `tests/test_middleware.py::test_missing_credentials_return_401` and
  `::test_concurrent_requests_do_not_share_credentials` already cover the three new tools with no
  test change required.
- **Idempotency**: `mimecast_list_policies` / `mimecast_get_policy` are `READ_ONLY` + idempotent
  (reused annotation, unchanged). `mimecast_manage_sender` uses `WRITES` with `idempotentHint=True`
  — calling permit/block again with the same `action`/`sender`/`to` is a no-op on Mimecast's side,
  the same idempotency class `mimecast_release_message` already claims.
- **Error handling**: reuses `classify_status` / `MimecastError` unchanged; a 403 (missing
  permission) already maps to `unauthorized` with no new code path.
- **Retries**: reuses `MimecastClient.call`'s existing policy unchanged — reads are retried on
  5xx/timeout, the managed-sender write is retried only on 429 (never on 5xx/network error), the
  same safety property `mimecast_release_message` already has (a write is never silently replayed
  after an ambiguous failure).
- **Logging / observability**: reuses `run_tool`'s existing per-call log line (tool name, outcome,
  status, latency) — no new logging code, and no new field is ever written to the log (sender/
  recipient addresses are passed to Mimecast but not logged, same as message ids today).
- **Security**: no new credential header; `mimecast_manage_sender` cannot be called without the
  same `X-Mimecast-Client-ID`/`-Secret` every other tool requires.
